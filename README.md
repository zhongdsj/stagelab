## 零、快速启动

> 本工具为 npm workspaces monorepo，三个包：`@fourstage/shared`（共享类型与 Zod Schema）、`@fourstage/server`（后端：MCP 服务 + HTTP 服务）、`@fourstage/web`（Vue3 前端）。

### 0.1 安装依赖（首次）

```powershell
npm install
```

### 0.2 启动后端

#### HTTP 服务（Web 前端用，默认端口 3000）

```powershell
# 开发模式（tsx 直跑，免构建）
npm run dev:http

# 生产模式（先构建再运行）
npm run build -w @fourstage/server
node packages/server/dist/http/server.js
```

> 默认监听 `0.0.0.0:3000`，可用环境变量 `PORT` 修改端口。

#### MCP 服务（AI 客户端接入，stdio 模式）

```powershell
npm run dev:mcp
# 或（生产）
node packages/server/dist/mcp/server.js
```

### 0.3 启动前端（端口 5173）

```powershell
npm run dev:web
```

> vite 已配置将 `/api` 代理到 `http://localhost:3000`，浏览器打开 `http://localhost:5173`，点「新建项目」创建项目后进入详情页。

### 0.4 常用脚本（根 package.json）

| 命令 | 作用 |
| ---- | ---- |
| `dev.bat` | 一键开启 3 个 cmd 窗口（MCP + HTTP + 前端） |
| `npm run dev:http` | 开发模式启动后端 HTTP 服务（端口 3000） |
| `npm run dev:mcp` | 开发模式启动 MCP 服务（stdio 模式） |
| `npm run dev:web` | 开发模式启动前端（vite，端口 5173） |
| `npm run build` | 依次构建 shared → server → web |
| `npm run typecheck` | shared + server 类型检查 |

### 0.5 完整开发启动

**方式一：双击 `dev.bat`**，自动开启 3 个窗口：
- `fourstage-mcp` → MCP 服务（stdio，日志走 stderr）
- `fourstage-http` → HTTP server（3000）
- `fourstage-web` → 前端（5173，代理 `/api`）

**方式二：手动分终端启动**

```powershell
# 终端 1：后端 HTTP 服务
npm run dev:http -- --repo "D:\some\repo"
# 终端 2：MCP 服务（可选）
npm run dev:mcp
# 终端 3：前端
npm run dev:web
```

> 后端启动时会自动从注册表（`%APPDATA%/fourstage/registry.json`）恢复历史仓库，故 `--repo` 可省略。

生产部署先执行 `npm run build`，再运行编译产物（`dist/` 下对应入口）。

### 0.6 运行日志

- HTTP server 输出每个请求日志（方法 / 路径 / 状态码 / 耗时）及启动、停止信息。
- MCP 服务因走 stdio 协议，stdout 是协议通道，日志统一写 **stderr**（工具调用 / 完成 / 失败），使用 `dev.bat` 时可从独立窗口查看。

## 一、项目解决的核心痛点

1. **AI 每次开发都重复学一遍系统 → 极高冗余 Token**：同一个系统，AI 每次会话都要重新 grep/read 探索，成本重复且无沉淀。
2. **无固定设计文档，AI 自由脑补需求 → 质量不可控**：缺少显式约束，AI 自行做决定，范围膨胀、遗漏关键约束。
3. **无结构化系统结构，改小错动全局 → 迭代风险极高**：改一处牵动全局，缺少结构图辅助影响分析。
4. **对话式上下文无限膨胀 → 越长开发越慢、越贵、越烂**：所有状态压进 LLM 上下文，迭代越多越膨胀，直到爆窗。
5. **无工程沉淀，做完即丢，不可回溯不可复用**：需求、设计、任务、变更、bug 无留存，无法追溯与复用。

------

## 二、项目终极设计哲学

1. **凡是模型会重复思考的，全部前置固化**：需求、约束、结构、任务在编码前固化为文档与结构化模型。
2. **凡是大体积数据，全部索引分片、按需加载**：索引→分片→完整三层访问，只把轻量摘要放进上下文。
3. **凡是系统结构，全部结构化建模、机器可读**：架构/类/流程图均为纯结构化 JSON，MCP 按 ID 局部读写。
4. **凡是开发流程，全部标准化四阶段锁边界**：S1 需求 → S2 任务 → S3 编码 → S4 修复，阶段间锁定范围。

> **本质**：把「AI 对话式即兴开发」升级为「AI 结构化工程化开发」。

## 三、背景：两种工作模式

**模式A：直接AI生成代码**
用户丢需求 → AI一次性输出大段代码；人复制粘贴。

**模式B：四阶段工作流**

- S1：需求讨论，产出开发文档（业务背景、目标、约束、数据模型、风险）
- S2：把文档拆成任务清单（每条任务：做什么、改哪些文件、验收标准）
- S3：按任务逐条编码实现，不越界做额外功能
- S4：bug定位修复、回归校验

> **本工具的核心定位**：把这套流程固化到项目实体、MCP接口、索引结构里。

## 四、结果层面对比

### 直接生成代码

✅优点

1. 上手快，交互轮次少；小需求可以快速拿到可用代码。

❌缺点

1. **需求理解不可控**：AI脑补大量隐含假设，很多业务约束、边界条件用户没口述清楚，AI自行做决定。
2. **范围膨胀**：经常额外加一堆你没提的功能；或者遗漏关键约束。
3. **没有验收标准**：AI输出代码，但没有定义"怎样算做完"，你只能靠人肉眼判断。
4. 修改迭代成本高：改需求时AI容易全盘重写，而不是增量修改；容易丢失原有逻辑。
5. **不可回溯**：没有留存：当初需求是什么、为什么这么设计、拆解了哪些任务。出bug很难追溯当初设计意图。
6. 复杂系统：大模块、多数据模型、多接口场景，很容易出现内部逻辑不一致，模型顾不全全局。

### 四阶段工作流

✅优点

1. **需求先固化（S1开发文档）**：把隐性想法变成显性文档，AI不能随意脑补；所有后续编码必须对齐文档。
2. **任务拆解（S2）做范围锁死**：S2输出任务清单，明确哪些文件改什么、验收标准；S3编码严格限定在任务范围内，禁止私自扩展功能。
3. **增量实现**：不是一次性生成整个系统，一条任务完成再下一条；每一步都有验收标准。
4. **完整可回溯**：项目保存文档、任务记录、变更记录、bug记录。后期改代码、排查问题可以回看当初设计意图。
5. **复杂项目质量显著提升**：多模块、数据模型、MCP服务、布局引擎这类复杂系统，把"思考"和"编码"分开，先想清楚再写代码。

❌缺点

1. 交互轮次变多；小简单需求会显得流程繁琐。
2. 如果S1文档写得差，后面S2‑S3全部会跟着错，上游质量决定下游。

> **结果差异小结**：
> - 小玩具demo：直接生成代码够用。
> - 要长期维护、多模块、有明确约束的工具项目（就是我们现在做的MCP管理工具）：四阶段产出质量、可维护性强很多。

## 五、Token消耗对比（重点）

> Token分两块：**输入token（你发给AI）** + **输出token（AI返回给你）**

### 模式A：直接生成完整代码

1. 输入：用户自然语言需求 + 少量现有代码片段
2. 输出：AI一次性吐出大量完整代码文件。

**Token特点**

1. **输出token很高**：一次性输出全部代码，大段代码输出。
2. 输入token前期低，但迭代会爆炸
   - 第一轮还好；
   - 当需要修改、修复bug时，你必须反复把大量上下文（旧代码、报错、你的想法）塞给AI；越往后输入token越来越膨胀。
3. **缺少结构化索引**：AI没有"项目索引"，没有分片；为了让AI理解全局，你不得不反复投喂大量源码。
4. 经常发生：为了改一小处bug，要把整个文件全部丢进去。

### 模式B：四阶段工作流（配合我们工具的索引/分片/MCP局部读取）

#### Token分布

1. **S1阶段：消耗一定输出token生成开发文档**，这是前期成本。
2. **S2阶段：输出任务文档，中等输出token**。
3. **S3编码：不再一次性生成全部代码；按任务局部读写，局部更新**。
4. **依靠项目索引，AI优先拿轻量索引摘要，按需拉取文档分片、部分图元、部分代码片段，不需要全量加载整个项目**。

#### 两种情况

**情况1：不做索引分片，纯文本四阶段（普通聊天框里手动四阶段）**

> 依然会消耗大量token。S1文档、S2任务文档、代码全部在对话上下文，上下文会持续膨胀。

**情况2：我们这套工具：MCP+ProjectIndex索引+分片+局部读取的四阶段** ✨核心优势

> 对话上下文不会塞大文档、完整图、完整源码。全部资源存在工具本地，AI通过MCP按需fetch。

- AI只把**轻量索引**读进上下文，索引只有摘要id列表，token很小。
- 需要哪个文档分片、哪几个图元、哪段代码，再通过MCP局部拉取。
- 更新图、更新文档、修改代码：使用局部patch，只传输变更片段，不传输完整对象。

> **本质：把大量状态移出LLM对话上下文，放到外部工具存储，AI按需加载。**

#### 两种模式对比关键点

- 普通聊天框直接生成代码：**所有状态全部压进LLM上下文，越迭代token越高，上下文窗口容易爆**。
- 我们工具的四阶段+MCP索引：**上下文只放当前正在处理的小块数据；项目完整状态保存在外部工具，显著降低每轮token开销**。

> **注意**：S1+S2会有前期token开销，但是随着项目迭代轮次越多，四阶段+索引分片模式的token优势会越来越明显。短期小需求反而吃亏。

## 六、对比总表

| 维度          | AI直接生成代码                       | 四阶段工作流（搭配本工具MCP索引）                        |
| ------------- | ------------------------------------ | -------------------------------------------------------- |
| 输出质量      | 小需求快；复杂系统容易脑补、范围失控 | 先固化需求，范围可控；复杂系统质量高                     |
| 可回溯性      | 差，没有设计、任务记录               | 完整留存文档、任务、变更、bug记录                        |
| 输出token     | 一次性输出很高                       | S1/S2前期消耗，S3/S4局部输出，单轮输出量小               |
| 输入token演变 | 迭代越多越高，经常全量投喂代码       | 依靠索引分片，按需拉取；不会无限膨胀上下文               |
| 出错模式      | 需求理解偏差，代码整体逻辑不一致     | 错误主要来自S1文档缺陷，可以回滚修正文档再重跑S2         |
| 适用场景      | 小demo、单文件脚本、一次性玩具       | 多模块工具、本地软件、需要迭代维护的项目（我们当前项目） |
| 轮次          | 轮次少                               | 轮次更多，流程更重                                       |

## 七、针对我们当前项目的现实启发

我们现在开发的这套工具本身，就是一个**多模块中等复杂度项目**：MCP服务、http接口、schema、存储层、elk布局worker、前端SVG渲染、索引分片。

1. 如果直接丢大需求让AI一次性生成整套系统： AI极大概率脑补大量实现细节，模块之间接口不一致；后续改bug每轮都要传入大量代码，token爆炸，并且没有设计回溯。
2. 使用四阶段： S1先写开发文档（当前已经完成）；S2拆解任务清单；S3逐条任务编码；S4修复bug；并且工具未来运行时，还会把这套模式提供给上层AI使用。

> **一个有意思点**：我们工具本身内部运行四阶段，同时工具对外MCP能力，又可以让别的AI客户端执行四阶段开发。

### 边界

- 如果只是写一个几百行小脚本，四阶段属于过度设计。
- 如果项目要分多个模块、有数据模型定义、未来要迭代维护，四阶段+外部索引存储的收益非常明显。

## 八、与 CodeGraph 的对比（定位边界）

> [CodeGraph](https://github.com/colbymchenry/codegraph)（colbymchenry/codegraph）：本地优先的代码知识图谱工具，用 tree-sitter 解析源码 AST，抽取函数/类/方法/类型为节点、调用/导入/继承为边，存入本地 SQLite（`.codegraph/codegraph.db`），通过 MCP/CLI/TS API 暴露给编程 Agent。

### 本质区别：代码的「现状镜像」 vs 开发的「意图记录」

| 维度 | CodeGraph | 本工具 |
|------|-----------|--------|
| 数据来源 | **代码**（tree-sitter 解析） | **人/AI 的决策**（需求、任务、方案、记录） |
| 回答的问题 | 代码**是什么**：谁调用谁、改这个碰哪里 | 项目**要做什么、为什么、改了什么、踩了什么坑** |
| 时间指向 | **当下**的代码快照 | **过去**（决策/变更）+ **现在** + **未来**（规划） |
| 产生时机 | 有代码之后 | 编码**之前**就已存在，贯穿全流程 |
| 图的含义 | 代码结构图 | **设计意图图**（架构/类/流程，先于代码存在） |
| 粒度 | 代码级符号（细） | 设计级模型（粗，人工可读） |
| 生命周期 | 单点查询 | **四阶段可回溯链路**（S1→S2→S3→S4） |

### 粗粒度图 vs 细粒度图：对 AI 的作用对比

| 维度 | CodeGraph 细粒度符号图 | 本工具粗粒度设计图 |
|------|------------------------|--------------------|
| 粒度 | 代码级符号（函数/方法/类型） | 设计级模型（模块/组件/类/流程） |
| 数据来源 | 源码 AST 机械抽取 | 人/AI 提炼的业务语义 |
| Token 成本 | 高（节点多、细节冗余） | 极低（几十个节点可一次载入） |
| 语义密度 | 低（细节淹没意图） | 高（直接给出系统意图） |
| 回答意图 | 不能（只反映代码现状） | 能（承载设计决策与流程） |
| 编码前可用 | 不可用（需先有代码） | 可用（设计先于编码） |
| 影响分析 | 符号级精确追踪 | 模块级快速定位上下游 |

**粗粒度图对 AI 的独特价值**（细粒度符号图无法替代）

1. **上下文压缩**：一个模块设计图 10-20 节点可完整放进一次 MCP 调用，对应源码需几十次 read；粗粒度图是给 AI 的"一览式地图"，避免盲人摸象。
2. **语义蒸馏**：粗粒度图是人工/AI 提炼过的业务语义（如"订单→校验→支付→发货"），不是代码的机械投影；AI 无需从代码里反向蒸馏业务意图。
3. **决策锚点**：编码前架构设计、任务拆解以图节点为锚；CodeGraph 依赖已有代码，覆盖不到设计期。
4. **可寻址共同语言**：图节点 ID 使 AI 与开发者沟通精确（"改模块 B 的 C 节点"），比大段文字省 Token 且无歧义。
5. **快速影响分析**：改模块前看粗粒度图即知上下游依赖，比翻代码定位更快。

### 本工具的价值落点

1. **没有代码时的设计**：架构/类/流程图设计时代码尚不存在，CodeGraph 依赖源码解析，结构性覆盖不到。
2. **意图与原因的丢失**：CodeGraph 能回答"谁调用谁"，但回答不了"为什么这么设计"——这些"为什么"只在四阶段产物里。
3. **未来规划与任务治理**：CodeGraph 是只读镜像，不承载需求文档、任务拆解、验收标准、变更记录。
4. **跨阶段可回溯**：S1→S2→S3→S4 是过程链路，CodeGraph 只有单一时间点的代码快照。
5. **历史决策沉淀**：代码合并后旧分支的设计决策、废弃方案会消失，本工具将其显式沉淀为文档与记录。

### 两者是互补，不是替代

> - CodeGraph 解决「AI **找不到代码**」→ 横向的代码空间理解
> - 本工具解决「AI **不知道要做什么、为什么、进度如何**」→ 纵向的项目生命周期治理

两者降 Token 作用于**不同环节**：CodeGraph 省的是"读代码"的探索 Token；本工具省的是"管过程"的传输 Token。本工具可选的扩展方向之一，是接入 CodeGraph 的符号索引与影响分析增强索引层，但完整图谱数据绝不进入 MCP 通道。
